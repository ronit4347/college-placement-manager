# Security audit

**Scope:** code-focused review of the existing FastAPI and React application, including authentication, authorization, request handling, resume storage, AI analysis, CORS, and database access. This is a point-in-time review, not a guarantee that the application is secure. It does not replace a penetration test, deployment review, or dependency vulnerability scan.

## Findings fixed

| Finding | Risk and affected files | Change and verification |
| --- | --- | --- |
| Example JWT secret was a known, usable value | Anyone using the example unchanged could sign tokens. `.env.example`, `backend/app/core/security.py` | Removed the usable example value; the application rejects missing or short keys when signing/verifying. Test checks the example has no secret. Generate a local value with `openssl rand -hex 32`. |
| Validation errors reflected submitted values | FastAPI's default 422 error could include invalid input, including a password with the wrong type. `backend/app/main.py`, `backend/app/core/errors.py` | Installed a handler that returns error locations/messages/types without input values or context. Regression test verifies a submitted password is absent from the response. |
| Login exposed JWT configuration details | A server-side setup exception was returned to the caller. `backend/app/api/routes/auth.py` | Return a generic authentication-unavailable response instead. Regression test covers missing JWT configuration. |
| Resume files relied on ambient filesystem permissions | Other local users could potentially read stored resumes depending on the process umask. `backend/app/services/resume_storage.py` | Restrict the storage directory to mode `0700` and files to `0600`, including existing regular files and new uploads. Existing local resume storage was restricted as well. Tests verify permissions. |
| Upload size was checked after multipart parsing | Large request bodies could consume temporary storage before the endpoint's file-size check. `backend/app/main.py`, `backend/app/core/errors.py` | Added a request-body cap for resume-upload routes before multipart parsing, bounded by the configured file limit plus multipart overhead. Tests exercise oversized requests, including a padded student-ID path. |
| CORS was broader than bearer-token use required | Credentialed cross-origin requests and wildcard headers were unnecessary. `backend/app/main.py` | Restrict origin to configured `FRONTEND_URL`, disable credentialed CORS, and allow only required methods and headers. Tests check the policy. |

## Controls inspected

- **Authentication and passwords:** Passwords are stored using `pwdlib`'s recommended Argon2 password hash. Login uses a dummy hash verification for an unknown account to reduce timing differences. Passwords are not returned by auth APIs. JWT uses a pinned HS256 algorithm, issuer and required `sub`/`iat`/`exp` claims; authenticated requests load the user from the database and check active status. Access token lifetime is configurable and capped at 24 hours (default 30 minutes). See `backend/app/core/security.py`, `backend/app/api/routes/auth.py`, and `backend/app/api/dependencies.py`.
- **Role access and IDOR:** Route dependencies enforce roles using the current database user, not a role claim supplied by the client. Reviewed student-owned resources, recruiter company scope, interviewer assignment scope, admin-only operations, and notification ownership. Resume and application access is scoped before returning records; inaccessible resources generally return not found/forbidden. Relevant routes include `students.py`, `applications.py`, `job_drives.py`, `interviews.py`, `offers.py`, `analytics.py`, and `notifications.py` under `backend/app/api/routes/`.
- **Registration and role provisioning:** Public registration schema rejects extra `role` fields and backend code assigns only `student`. Recruiters are created only by an admin through company assignment. Admin-controlled interviewer provisioning now has a dedicated route; public registration cannot create privileged accounts. See `docs/authorization.md`.
- **Validation and query safety:** Pydantic request schemas and service-level business checks validate input. Database access uses SQLAlchemy expressions and bound parameters; no user-controlled SQL interpolation was found. Migration SQL is static. Validation responses now avoid echoing request values.
- **Uploads:** Resume upload checks allowed type/extension, PDF signature, maximum size, and generates a random storage name rather than trusting the supplied filename. Access to the resume routes is authenticated and scoped. The request-level size cap also prevents oversized multipart bodies from being fully spooled first.
- **CORS and secrets:** CORS is restricted to the configured frontend origin. Secrets and database connection details are read from environment settings; `.env` is ignored by Git and `.env.example` contains placeholders. The AI provider key is backend-only (`AI_API_KEY`) and is not part of frontend configuration or responses.
- **AI analysis and errors:** Analysis is limited to the authenticated student's own resume and an eligible published job context. The service sends only the text/context needed for analysis, asks for structured output, validates the response, and handles provider failures without returning credentials. AI output is advisory and does not change candidate status. Resume PII removal is heuristic, not guaranteed anonymization.
- **Database lifecycle:** SQLAlchemy sessions are request-scoped and closed. The database URL comes from configuration. No user-provided SQL fragments were found in routes/services reviewed.

## Remaining risks and deployment actions

1. **No shared rate limiting:** Login, registration, and AI analysis can be repeatedly called. Add rate limits at a gateway or use a shared limiter suitable for multi-worker deployment; an in-process counter would not reliably protect a production deployment. Registration's duplicate-email response can also reveal whether an address exists.
2. **Browser token exposure:** The frontend keeps its bearer token in `sessionStorage` (`frontend/src/services/auth.ts`). This avoids persistent local storage, but JavaScript running in the origin can still read it. No unsafe HTML rendering was found in the reviewed UI. Keep dependencies patched, deploy a strong Content Security Policy, and consider a backend-for-frontend with HttpOnly cookies if the threat model requires it.
3. **Token revocation:** Logout removes the token in the browser. A copied token remains usable until expiration; there is no server-side token denylist. Account deactivation is checked against the database on authenticated requests.
4. **Infrastructure protections:** Configure PostgreSQL TLS with certificate verification and a least-privilege database role. Protect resume storage and backups with encrypted disks/backups and restrictive access. Application file permissions do not encrypt resume contents at rest.
5. **AI privacy:** Resume text can contain personal information. Redaction is heuristic and cannot guarantee removal. Use the mock mode unless external processing is approved; if a provider is configured, review its retention and data-processing terms and minimize submitted text.
6. **Dependency and deployment review:** This work did not run a dependency CVE scanner or inspect production proxy, TLS, host, database, backup, or secret-manager configuration. Add dependency scanning for Python and npm packages in CI and review production configuration before deployment.

## Verification

The backend test suite includes security regression coverage for validation response redaction, missing JWT configuration, CORS policy, upload body limits, resume storage permissions, authentication, role checks, and resource ownership. At the time of this audit, `pytest` completed with **59 passed**. These tests cover known behavior; they are not proof of absence of vulnerabilities.
